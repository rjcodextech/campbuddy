# 9. Admin panel

[← Back to index](../SKILL.md) · Previous: [8. Security & privacy](08-security-privacy.md) · Next: [10. API specification →](10-api-specification.md)

Full CRUD on events, not just approve/view — an admin is never limited to what an automated job discovered:

| Section | Capability |
|---|---|
| Events — **Create** | Add a new event manually (slug + source site URL), independent of central discovery ([5.3](05-system-architecture.md#53-central-event-discovery)). |
| Events — **Read** | List all events with status (draft/approved/active/archived) and visibility (enabled/disabled, [3.2](03-functional-requirements/02-branding.md) BR6), **ordered by event day** (soonest first) and filterable/searchable — see the *Events list* note below. |
| Events — **Update** | Edit slug, display name, source site URL, lifecycle status, logo/favicon upload (overrides auto-fetch per [3.2](03-functional-requirements/02-branding.md) BR5), and the **frontend visibility toggle** (default on, BR6). *(Color fields described in earlier drafts were removed — see [3.2](03-functional-requirements/02-branding.md).)* |
| Events — **Delete** | Hard delete is allowed only for `draft` events with no ingested data yet. An `approved`/`active`/`archived` event can only be **archived**, not hard-deleted; archiving already purges roster data per [8.4](08-security-privacy.md#84-ingested-roster-data--explicit-policy). |
| Ingestion status | Per-event last roster-fetch time/status, last speaker/sponsor-fetch time/status, manual "Refresh now" per event, manual "Re-fetch branding assets" separate from the daily data refresh — both run immediately and report the outcome (no queue worker needed). |
| Cache & fresh data *(Dashboard)* | One **Purge cache & refresh data** button: clears server caches, re-fetches every live event's schedule/speakers/sponsors/event info, optionally purges Cloudflare, and tells every open or installed app to drop its saved copies and reload. Shows when it was last used, by whom, and what it did. Details below. |
| Roster suppression | View/search the ingested roster for an event, manually suppress an entry ([8.4](08-security-privacy.md#84-ingested-roster-data--explicit-policy) takedown path). |
| Event managers *(added Sept 2026)* | An admin creates **event manager** accounts (name, email, phone, password, and one or more WordCamps) — nobody registers. A manager signs in on their own page (`/manager/login`) and can edit only their events' **Event details**, **Event information** and **Quests & checklist** — never an event's status. See the *Event managers* note below. |
| Quest editor | Full CRUD on event-specific quests per event ([3.6](03-functional-requirements/06-quest.md) C1, C3) — add, edit, reorder, delete. Default/cross-event quests are seeded, not per-event admin content. |
| Offers | Full CRUD, filtered/scoped by event, plus (post-launch) a per-deal `capture_leads` toggle — see [3.7](03-functional-requirements/07-deals.md). |
| Deal Leads *(added post-launch)* | Per-event, filterable by deal and date range, with a CSV export — captured Name/Email/Mobile submissions from deals with lead capture enabled. See [3.7](03-functional-requirements/07-deals.md). |

> **Current implementation note (redesign):** the admin panel was rebuilt on one small design system instead of per-page styling, so every page looks and behaves the same:
>
> - **Tokens & classes** — brand colours live in `tailwind.config.js` (`ink`, `paper`, `line`, `maroon`, `navy`, `teal`, plus a distinct `danger` red so *Delete* never looks like the maroon *Save*); shared form/button/table classes are `.cb-*` in `resources/css/app.css`. Views must not hard-code stock Tailwind palette colours (a test enforces it).
> - **Components** (`resources/views/components/`) — `<x-button>` (variants: primary · secondary · danger · danger-outline · link), `<x-action-form>` (a one-button POST/PUT/DELETE form with optional confirm), `<x-card>`, `<x-alert>`, `<x-badge>` / `<x-event-status>`, `<x-table>` + `<x-table.empty>`, `<x-stat>`, `<x-icon>`, and `<x-form.input|textarea|select|checkbox|file|password>`, which handle labels, hints, `old()`, inline errors and `aria-*` uniformly. `<x-admin.event-nav>` is the tab strip (Details · Quests & checklist · Deals · Roster · Deal leads) shared by every event sub-page.
> - **Layout** — responsive: off-canvas drawer navigation on phones, breadcrumbs + title + actions header, skip link, flash messages and a validation-error summary rendered centrally (so pages can't forget them). `noindex` on all admin pages.
> - **Sign-in** — branded two-panel screen with show/hide password, a "signing in…" state that blocks double submits, correct autofocus after a failed attempt, and matching forgot/reset/confirm screens. Auth *mechanics* (throttling, remember-me, no public registration) are unchanged.
> - **Dashboard** — now real: event counts by status, drafts awaiting approval, roster and lead totals, recently updated events, and a one-line summary of what is failing (the detail lives on the **Errors** page — see below).
> - **Behaviour fixes made along the way** — the quest/offer forms now show validation errors (previously they failed silently); *Active* / *Require contact info* can actually be switched **off** (unticked boxes used to send nothing, so the change was ignored); new quests/deals are appended after existing ones, and both have an *Order* field.
> - **Default checklist** — the Quest editor opens pre-filled with the 9-item checklist every event starts with ([3.6](03-functional-requirements/06-quest.md)); admins edit those rows like any other quest.
>
> **Current implementation note (Events list & Errors page):**
>
> - **Order** (`App\Support\EventListing`) — upcoming and ongoing events first, the one that starts soonest on top; events that are over follow, most recent first; events with no date last. "Over" = the last day (`ends_on`, or `starts_on` when there is no end date) is before today (app time zone; plain dates, not `EventTime`). Ties fall back to name, then id.
> - **Filters** (GET query string, so a filtered list can be bookmarked): `q` (name / slug / short name), `status`, `visibility` (`visible`/`hidden`), `when` (`upcoming`/`past`/`undated`). Unknown values are dropped, never trusted. Pagination keeps them.
> - **Highlight** — the 10 nearest upcoming/ongoing events (any status) get a tinted row with a left bar (`.cb-row-soon` in `resources/css/app.css`); the first not-yet-started one is badged *Next up*, one that is on today *Happening now*. The ten are computed over all events, not the filtered page, so they stand out under any filter. The Dates column also says *In 5 days* / *Tomorrow* / *Ended 3 days ago*.
> - **Errors page** (`/admin/errors`, `Admin\ErrorsController`, `App\Support\ErrorReport`) — *System checks* (the `SystemHealth` problems: cron, migrations, queue, failed jobs, live events without data or time zone, each with its fix command) and *Fetch problems* (failed or partly-failed fetches, one row per repeated failure with a count and last-seen time; filters: period 24 h / 3 d / 7 d — the log is kept for 7 days, see [7](07-data-model.md) — event, what failed, result). The dashboard only shows one line — "N problems need attention — View errors" (red when a system check is failing, amber otherwise, a quiet green "No problems" when clean).

> **Current implementation note (Analytics page, 6 Oct 2026):** Admin → **Analytics** (`/admin/analytics`, `Admin\AnalyticsController`, `App\Support\AnalyticsReport`, admin only, `throttle:30,1`) reads the GA4 property through the Data API (`analytics.readonly` scope, same service-account JWT flow as `campbuddy:ga-setup`; token cached 50 min). The property has **two web streams** — CampBuddy (`G-1YHQ19XV0P`, campbuddy.club) and WPSimplified (`wpsimplified.in`) — so every report is filtered by `streamId`; the stream dropdown is listed live from the Admin API (cached a day), the stream whose measurement ID is `GA_MEASUREMENT_ID` first. Dates: today, last 7/10/30/90 whole days (ending yesterday) or custom (≤ today, ≥ ~14 months back; bad dates fall back to 10 days with a note). **Hide bots** (on by default) drops screen sizes only bots report (`AnalyticsReport::BOT_SCREENS`). ~30 reports go in batches of 5 (`batchRunReports`) and the result is cached an hour per (stream, dates, bots); "Fetch again now" (`?fresh=1`) refetches. Sections: headline tiles, people per day, WordCamps (slug → display name), sources, cities/countries, devices, first-visit source, pages with time per person, hour/weekday, and — only when the stream has the app's own events — in-app actions (zeros shown), tabs, saved sessions, quests, deals/Free Steals, sponsors, guide depth, FAQ, install/reminders, Web Vitals, errors; then every event name. Missing setup or a Google error shows a message with what to fix, never a 500. Server needs `GA_PROPERTY_ID`, `GA_CREDENTIALS_PATH` and a **Viewer-only** service-account key (DEPLOYMENT.md). Tests: `AdminAnalyticsPageTest`.

> **Current implementation note (Event managers):** Admin → **Event managers** (`Admin\EventManagerController`, `/admin/event-managers`) lists, creates, edits, switches off and deletes them; the form takes name, email (stored lower-cased, unique), phone, password (min 8; blank on edit keeps the old one) and a tick-list of every event (soonest first, with a filter box; at least one on create). The manager's own area lives in `routes/manager.php` under `/manager`:
>
> - **A separate account type and guard, on purpose.** Managers are rows in `event_managers` (`App\Models\EventManager`), not in `users`, and sign in through the `manager` guard (`config/auth.php`). Every existing admin route and policy treats *any* `User` as an admin, so a manager in `users` would have been an admin; on their own guard they cannot pass `auth` or any policy. Signed in as a manager is *not* signed in as an admin, and the other way round; both can be signed in at once in one browser.
> - **Pages** — sign-in `/manager/login` (its own layout, throttled 5/min plus a per-email+IP limit, one vague error for wrong / unknown / switched-off), **My events** `/manager` (cards, soonest first; a manager with exactly one event goes straight to it), and per event three tabs: **Event details** (display name, slug, short name, source site URL, dates, time zone, *Visible in the public app*; the status is shown read-only), **Event information** (the same fields and limits as the admin's card, no *Fetch latest* button) and **Quests & checklist** (add / edit / hide / remove).
> - **Status is never accepted.** The details form request has no `status` rule, so `validated()` cannot contain it; a forged `status` field is ignored (tested). The slug, source URL and visibility *are* editable by a manager (owner's decision, 2026-09-26) — the slug field warns that changing the event's address breaks old links and QR codes.
> - **Only their own events.** There is no `{event}` model binding: every controller finds the event through `$manager->events()`, so another event — or a quest of another event, looked up through the event's own quests — is a plain 404, and a form request for an event that isn't theirs is a 404 *before* validation runs (nothing leaks). `EnsureEventManager` (the `manager` counterpart of `auth`) also signs a manager out on the next request when an admin switches them off or changes their password (a fingerprint of the password hash lives in the session).
> - **No self-service password.** There is no forgot-password or change-password page for managers (mail is log-only on the live host; the owner chose "admin only", Sept 2026); an admin sets a new password on the manager's page, which also invalidates open sessions and the "keep me signed in" cookie.
> - **What a manager may type is limited.** *Source site URL*: only `https://…wordcamp.org` (or a subdomain) — no other domain, no login details in the URL, no odd port (`App\Rules\WordCampUrl`) — because everything the app shows from a WordCamp is fetched from that address; an address an admin already set stays saveable as it is, and admins are not held to the rule. *Display name* and *short name*: plain single-line text, no `< > [ ]` (they go into `<title>`, `llms.txt`'s Markdown, the manifest). Passwords set by an admin: 8–72 characters.
> - **Activity log (Admin → Event managers → Activity).** Every real change a manager saves is written to `event_manager_changes` — who, which event, which section, and a one-line summary: old → new for the details fields (name, slug, dates, source URL, time zone, visibility), only the *names* of the information fields that changed, and add / rename / move / hide / show / remove for checklist items. Saving without changing anything writes nothing; refused requests write nothing. The admin sees it as a filterable page and as a card on each manager's page; the manager's name is copied into the entry so it outlives the account. Entries older than 90 days are removed as new ones are written (`App\Support\ManagerActivity`, no scheduled job). A failure to write an entry is reported but never blocks the save.
> - **Abuse limits.** Saves are capped at 60 a minute *per manager* (`ThrottleManagerWrites` — per manager, not per address, because a venue's wifi puts a dozen organizers behind one address; each save clears the caches behind the event's attendee pages); sign-in allows 30 attempts a minute per address plus 5 wrong tries per email + address (so a dozen organizers can sign in from one wifi); a time-zone change on an active event queues the schedule re-fetch at most once in five minutes. Every manager page is sent `Cache-Control: no-store, private`, so the Back button after signing out shows the sign-in page.
> - **Attendees see a change at once.** Details and information saves clear the event's data version and the sitemap / llms.txt caches; every checklist change clears the data version too, so open apps pick it up at their next check instead of after the 2-minute cache. (A *removal* alone does not change the version's fingerprint, which is built from "last updated" times — the same as when an admin removes an item; a reload shows it.)
> - **Not ready yet ≠ broken.** If the code is uploaded before its migration, Admin → Event managers and the Activity page say what to run instead of a 500, and manager saves still go through (the log write is skipped); the Errors page lists the pending migration, and a health check ("Event manager sign-in isn't set up") flags a stale cached config or route list, with the fix `php artisan optimize:clear && php artisan optimize`.
> - `EventListing` orders the manager's events like the admin list; `EventEdits` writes the time zone (`timezone_locked`), the dates (`dates_locked`) and the info JSON exactly as the admin's own pages do — a test posts one payload to both and compares. A time-zone change on an active event queues the schedule re-fetch, as for an admin.

> **Current implementation note (Purge cache & refresh data):** Dashboard → *Cache & fresh data* card → `POST /admin/cache/purge` (`Admin\CachePurgeController` → `App\Services\CachePurger`). In order:
>
> 1. **Server caches** — `php artisan optimize:clear --except=compiled`: application cache, compiled views, cached config/routes/events. `compiled` (the service manifests in `bootstrap/cache`) is deliberately skipped: deleting them can leave a host where the web user can't rewrite that folder unable to boot.
> 2. **Live data is never blanked.** The ingested schedule *lives in* the application cache, so it is set aside before the flush and put back after; the fresh fetch replaces it only when it succeeds. If a WordCamp's site is down at that moment, attendees keep the last good schedule and the admin is told which event couldn't be refreshed.
> 3. **Fresh data now** — for each approved/active event: sessions/speakers/sponsors (active only) + event information, synchronously within a 30-second budget (well inside Cloudflare's ~100 s origin timeout); anything beyond the budget goes to the queue. The attendee roster is *not* re-scraped (IN2: once daily).
> 4. **`public/storage` link** — attempts `storage:link --relative` if the link is missing (best effort; hosts often disable `symlink()`; files are still served by `PublicStorageController`).
> 5. **Cloudflare** — if `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_API_TOKEN` are set, `purge_everything` on that zone (token needs only *Zone → Cache Purge → Purge*). Not configured → the card says so. A Cloudflare failure is reported but doesn't undo the rest.
> 6. **Tell the phones** — bump the *cache version* (`App\Support\CacheVersion`, a file in `storage/app/private/cache-purge.json`: a millisecond timestamp plus who/when/summary — kept out of the application cache precisely because the purge empties that). Every attendee page carries it as `<meta name="campbuddy-cache-version">`; `resources/js/attendee/cache-version.js` compares it with the newest version that device has seen (localStorage) and, if newer, **replaces** the saved pages with fresh copies in place (`saved-copies.js` — the hashed `/build/` files never go stale and are left alone); **nothing is deleted first**, so a phone with a poor connection keeps every page it had ([23](23-data-retention.md)). An app left open in the background also asks `GET /api/v1/cache-version` when it returns to the foreground (at most once a minute) and reloads if a purge happened meanwhile. **Never touched:** attendees' saved sessions, quest progress, Camp Card (IndexedDB on their own phone).
>
> Rate limiting is a 10-second cooldown (read from the version file) plus a cache lock against double-clicks — *not* the `throttle` middleware, whose counters live in the very cache a purge empties, so each purge would reset its own throttle.

> **Media Library: what uses each image (30 Sep 2026).** Admin → Media Library (`Admin\MediaController`) shows on every image where it is used — deals (an event's own or a default deal) and Free Steals, via `MediaAsset::offers()` / `freeSteals()` — as "In use · N" with the names, or "Not used". Filter links All / In use / Not used (`?show=used|unused`, with counts). Only a "Not used" image has **Delete** (`DELETE /admin/media/{media}`, confirm first): inside a locked transaction it checks again and refuses an image in use ("That didn't work" alert), otherwise deletes the row and then the file. This replaced the earlier "the library never deletes" rule; the owner confirmed it twice. A deleted shipped logo (default deals, Free Steals) is not put back by the migrations on its own. Tests: `MediaLibraryUsageTest`.
