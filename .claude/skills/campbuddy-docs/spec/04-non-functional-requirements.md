## 4.1 Accessibility

Sensible WCAG practices, at minimum: sufficient color contrast, full keyboard accessibility, semantic HTML, labeled form fields, accessible buttons (not bare clickable `<div>`s), alt text on meaningful images, visible focus states, screen-reader-friendly document structure, touch targets sized for real thumbs on a real phone, and `prefers-reduced-motion` respected on any hover/transition animation.

## 4.2 Performance

Optimize aggressively — this app gets used on congested venue wifi by many people at once:

- Small initial payload; lazy-load anything non-critical.
- Optimize images (this is why branding assets are downloaded and re-hosted rather than hotlinked, [3.2](03-functional-requirements/02-branding.md) BR4 — CampBuddy controls their size/format, not the source site).
- Minimize API calls; cache event data client-side and work from the cached copy rather than re-fetching unchanged information (this is the entire point of the stale-while-revalidate + CDN design in [5.4](05-system-architecture.md#54-cdn--now-mandatory-not-optional)).
- Avoid large JS dependencies for trivial functionality — vanilla JS stays the default ([5.5](05-system-architecture.md#55-asset-build--laravels-default-vite-pipeline)); a library is justified per-case, not by default.
- Navigation between tabs should feel immediate — no visible loading spinner for data that's already been downloaded this session.

## 4.3 Error handling & empty states

**Errors:** user-facing messages are always friendly and actionable — never a stack trace, raw PHP warning, JSON error body, SQL message, or a technical network exception string. Translate, don't expose: not *"FetchError ECONNREFUSED"* but *"We couldn't refresh the latest event information. Your saved CampBuddy data is still available."* This is the same "guidance over information" principle ([1.0](01-project-overview.md#10-product-philosophy)) applied to failure states, not just happy-path content.

**Empty states:** every major screen needs one — a blank screen is never acceptable. Examples already speced inline: My Day ([3.8](03-functional-requirements/08-my-day.md)), Camp Card ([3.10](03-functional-requirements/10-camp-card.md) CC6), Quest ([3.6](03-functional-requirements/06-quest.md) C5). The same standard applies to Explore's People/Sponsors/Deals tabs and Contribute before the attendee has answered anything.

## 4.4 Offline-first

Once an event's data has been downloaded, these must keep working with zero connection: Home's guidance ([3.1](03-functional-requirements/01-home.md), from already-downloaded data), the event schedule and My Day ([3.8](03-functional-requirements/08-my-day.md)), Quest ([3.6](03-functional-requirements/06-quest.md)), Contribute's team info ([3.9](03-functional-requirements/09-contribute.md)), Camp Card ([3.10](03-functional-requirements/10-camp-card.md)), the attendee's own onboarding preferences ([3.11](03-functional-requirements/11-onboarding.md)), and any sponsor information already downloaded ([3.12](03-functional-requirements/12-sponsors-event-info.md) EI1).

Network-dependent features degrade gracefully instead of breaking: if Explore → People ([3.4](03-functional-requirements/04-matching.md)) can't reach `/api/v1/events/{slug}/discovery`, the app doesn't show a raw error — it shows something like *"You're offline. Your CampBuddy still works — attendee discovery will refresh when you're connected again."*

> **Current implementation note (service worker, `public/sw.js`, cache `campbuddy-v2`):** pages are network-first with a saved-copy fallback — with a saved copy the network gets 4 s before the copy is served (flaky conference wifi), and a 5xx from the server also falls back to the saved copy (a 404 is a real answer and isn't masked); a never-visited page that can't be reached gets a small "You're offline" page instead of the browser's error. Hashed `/build/*` assets are cache-first. **Only plain 200, non-redirected responses are ever stored** — a cached 404/500 (for a hashed asset, forever) or a redirect that can't be replayed for a navigation are how the previous worker could get stuck. **`/admin`, `/api/` and `/up` are never intercepted or cached** — admin pages are signed-in and per-user. Bumping the cache name deletes every older cache on activation, which also cleared any admin HTML the earlier worker had stored. Push payloads that aren't valid JSON are ignored rather than throwing. An admin's *Purge cache* reaches installed apps by deleting Cache Storage ([9](09-admin-panel.md)); offline data the attendee created (saved sessions, quest progress) is in IndexedDB and is never touched.

## 4.5 UI/UX constraints

Mobile-first, fast, clean, friendly, modern, easy to scan, touch-friendly, visually polished — designed for someone walking around a venue with one hand on their phone. Explicitly avoid: cramped layouts, a desktop-style admin-panel look bleeding into the attendee-facing app (that look is fine for `/admin` itself, [5.5](05-system-architecture.md#55-asset-build--laravels-default-vite-pipeline) — never for the attendee side), walls of text, excessive modals, tiny tap targets, settings nobody asked for, excessive animation, or an overly corporate tone. Use progressive disclosure — show what's needed when it's needed, not everything at once.

> **Current implementation note:** the attendee app is **full width (100%) at every viewport size** — no centered phone-column/card frame and no separate desktop layout (earlier versions capped it at 428px, then gave desktop a 1040px frame with a left-sidebar nav; both were dropped). The tab bar stays pinned to the bottom of the frame at every width. The "/" WordCamp picker sits in the same `.app-frame` as the event pages (`layout/_app-frame.scss`, `layout/_bottom-nav.scss`). Because the app is designed for a phone, laptop/desktop visitors — a viewport ≥1024px with a hovering, precise pointer, so not tablets or narrow windows — get a dismissible "CampBuddy is designed for your phone" notice with a QR code of the current page at the top of every page (`partials/desktop-notice.blade.php`, `components/_desktop-notice.scss`, `js/attendee/desktop-notice.js`); dismissal is remembered in `localStorage`.

> **Current implementation note (phone layout — iPhone & Android):** the page is an ordinary scrolling **document**, not a 100vh box with its own scrollbar (that hid the tab bar under Safari's bottom toolbar and stopped the browser chrome collapsing). The tab bar is `position: fixed` to the bottom (`layout/_bottom-nav.scss`) — always visible, at every scroll position and width; `.app-frame--with-nav` reserves room under the content and `--bottom-nav-space` (bar height + `env(safe-area-inset-bottom)`) is the one shared number for the bar, the page padding, the toast and `html { scroll-padding }`. `.app-frame` uses `overflow-x: clip` (never `hidden` — that makes it a scroll container and silently disables the sticky top bar). Heights use `dvh` with a `vh` fallback; left/right `safe-area-inset` padding keeps content off the notch in landscape; `touch-action: manipulation` removes double-tap zoom; `:hover` styles go through the `hover` mixin (`@media (hover: hover)`) so a tap doesn't leave a button stuck in its hover colours; interactive controls are ≥44px tall (the session ★ and title, social icons and the top-bar pills reach it via padding/hit areas); at ≤359px the top bar stays one row and the tab bar top-aligns its icons so "Camp Card" can wrap. Three global fixes worth knowing: `[hidden] { display: none !important }` (component `display` rules used to override the attribute — the "Install app" button showed on every device), `dialog { margin: auto }` (the reset's `* { margin: 0 }` had pinned every dialog to the top-left corner), and the toast has an explicit `width: max-content` (a `left: 50%` box was squeezed into half the screen).
>
> **Current implementation note (the "Install app" button, `js/attendee/install.js`):** Chrome/Edge/Samsung/Opera on Android and desktop fire `beforeinstallprompt` — the button appears then and opens the browser's install dialog; if that dialog is dismissed the button stays and the next tap shows the browser-menu steps (a prompt can only be used once). **Every iPhone/iPad browser** (Safari, Chrome, Edge, Firefox; iPadOS is detected by its Mac-style user agent + touch) and **Firefox on Android** never fire it, so the button is always shown there and opens a dialog with the manual steps (`tpl-install-dialog` in `templates/shared.blade.php` — one dialog, three step lists, only the matching one kept). **In-app browsers** (Instagram, Facebook, LinkedIn, Snapchat, WeChat, Android WebViews…) can't install anything, so the button says to open the page in Safari/Chrome first. Nothing shows when already installed (standalone) or on a desktop browser that can't install web apps (Firefox, Safari). Installing needs **HTTPS in production** (`APP_URL=https://…`; `localhost`/`127.0.0.1` also count as secure for testing — `http://campbuddy.test` does not, and Chrome reports `not-from-secure-origin`), the manifest, the root-scoped service worker with a fetch handler, and the 192/512/maskable PNG icons — all verified installable with Chrome's own `Page.getInstallabilityErrors` (no errors) on both the picker and an event page.

## 4.6 Data synchronization

When connectivity returns: refresh outdated event data, sync explicitly-shared discovery data where applicable ([3.4](03-functional-requirements/04-matching.md)), and never touch local Quest/My Day/onboarding state beyond what the attendee changed themselves. Reconnecting must never interrupt whatever screen the attendee is currently on — no forced reload, no lost scroll position.

> **Current implementation note (one form pattern across the attendee app):** every form and choice-chip group in the attendee app now follows the pattern first built for the Camp Card editor, so no page looks or behaves differently by accident. It applies to **onboarding** (the picker page), the **discovery join/edit form**, the **deal-lead dialog**, **roster removal**, **Contribute's** "what do you enjoy" chips, and **My Day's** search box and filter chips (Camp Card's editor is the fullest example).
>
> - **Structure & styles** — `resources/scss/components/_form.scss` holds the controls, groups (`.form-group`: a titled card with a short description) and fields (`.form-field`: label above, control, optional hint, error line that only appears when needed, and a fixed-prefix adornment such as the "@" of a handle). `_pill.scss` holds the choice chips. `attendee/partials/form-field.blade.php` builds a labelled text field, so labels, hints and spacing can't drift.
> - **Controls** — every text input, select and textarea is at least **44px tall at 16px type** (smaller makes iOS Safari zoom the page on focus) with a brand-coloured focus ring, a red border when invalid, and the right `autocomplete` / `inputmode` where it matters (name, email, tel on the deal-lead form). The two search boxes (My Day, Explore → People) share one style with a magnifier icon.
> - **Choice chips** are `<button type="button" aria-pressed>` inside a labelled `role="group"`, and a selected chip shows a **✓** as well as the colour change (state is never carried by colour alone). My Day's three filter rows each get a small DAY / TRACK / SESSION TYPE label.
> - **Limits match the server.** The discovery join form now stops at **5 tags** with a message — the API (`StoreDiscoveryRequest`) rejects more, and the form previously let people pick up to 10 and then failed on save with a misleading "check your connection" error. Its Profession / Who-to-meet fields carry the API's own maximum lengths (100 / 255). Discovery tags stay lowercase in the data and are displayed capitalised.
> - **Adding a form:** use `.form-group` / `.form-field` and the partial rather than bare inputs; put `aria-pressed` on toggle chips and toggle `.chip--selected` alongside it.
