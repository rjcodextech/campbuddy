# 3.2 Event branding

[← Index](00-index.md) · Previous: [3.1 Home](01-home.md) · Next: [3.3 Attendee roster ingestion →](03-roster-ingestion.md)

> **Current implementation note (supersedes BR1, BR2, BR7 below):** per-event **color** theming was removed after launch, by explicit product decision. Every event now shares one fixed CampBuddy palette and typography system — only the event's own **logo** and **display name** still vary per event (logo shown on Home's hero and in Explore → Event Info; the global topbar always shows CampBuddy's own mark, never the event's). BR3–BR6 (fallback behavior, auto-fetch, admin override, visibility toggle) are otherwise still accurate.

| ID | Requirement |
|---|---|
| BR1 | ~~Every event record carries: display name, short name/hashtag, primary/accent color, logo asset, favicon asset.~~ Color fields were later dropped from the schema; display name, short name, logo, and favicon remain. |
| BR2 | ~~The active event's branding (including color) is applied to CSS custom properties at load time.~~ Only logo/name are event-specific now; the color palette is fixed app-wide. |
| BR3 | Fallback: if an event has no logo set, the app uses CampBuddy's default icon — never a broken/unstyled state. |
| BR4 | **Best-effort auto-fetch**, run once when an event is approved (see [finding 0.6](../00-findings.md), not on the daily schedule): try the event site's REST `site_icon_url` first (cheap, works when set); if absent, parse the homepage `<head>`/header markup for the site logo `<img>` and a favicon `<link rel="icon">`; if that also fails, fall back to `/favicon.ico` at the site's domain. Whatever is found is **downloaded and re-hosted on CampBuddy's own storage** — never hotlinked — so the event's own site going down later doesn't break CampBuddy's branding. |
| BR5 | **Admin can always upload/replace the logo and favicon manually**, overriding whatever auto-fetch found (or filling the gap if auto-fetch found nothing). This is a deliberate reversal of V1's "brand assets aren't admin-manageable" limitation — scoped specifically to per-event logo/favicon, not CampBuddy's own app-wide icon/mascot, which stays a file-replace + redeploy as in V1. |
| BR6 | **Frontend visibility toggle**, independent of the event's lifecycle status (draft/approved/active/archived, [7. Data model](../07-data-model.md)): a simple enabled/disabled switch controlling whether the event appears in the public app at all. **Default: enabled** — every approved event is visible unless an admin explicitly turns it off. This lets an admin approve/ingest an event without immediately publishing it, or temporarily hide one without touching its data or lifecycle state. |
| BR7 | Branding stays bounded: only the logo and event name vary; CampBuddy's own layout, color palette, type scale, and component shapes stay constant across every event — an attendee should always recognize it as CampBuddy first, the specific WordCamp second. This is a stronger version of the original "bounded branding" intent (which allowed per-event colors within a contrast guardrail) — see the note at the top of this file. |

> **Current implementation note (logos that actually render, and the install identity):**
>
> - **Root-relative, versioned URLs.** `Event::logoUrl()` / `faviconUrl()` return `/storage/branding/{id}/logo.png?v=<file mtime>` — no host or scheme, so a wrong `APP_URL` (http vs https, www vs apex) can't produce mixed-content or cross-origin images (which would also taint the Camp Card canvas export). The `?v=` changes only when the file does, so a re-fetched or re-uploaded logo isn't hidden by browser/CDN/service-worker caches. `Event::markUrl()` = favicon, else logo (used for the picker's avatar); the Camp Card's QR-centre icon stays favicon-only because it is drawn into a square.
> - **Served without the symlink** — see [12](../12-deployment.md) (`PublicStorageController`). The framework's own `/storage` route for the private `local` disk was also switched off (`serve => false`): it shadowed the public disk's URLs and 404'd them.
> - **BR3 fallback, enforced client-side too.** Every event image carries `data-fallback="/media/icons/icon-192.png"`; `resources/js/attendee/image-fallback.js` swaps a failed image to it (also sweeping images that failed *before* the script ran), once, never looping.
> - **BR4 fires whenever an event goes live** (approved *or* active, by any route incl. the lifecycle sweep, or created that way) with `onlyMissing`, so an admin's upload is never overwritten; plus a daily 02:30 backfill; the admin's **Re-fetch branding** button still replaces both and runs immediately. One unreachable asset host no longer stops the other asset. Storing a new file deletes the previous one even if the extension differs (`Event::storeBranding`).
> - **SVGs are refused if executable** (`<script>`, `on*=` handlers, `javascript:`, `<foreignObject>`, entities) — both auto-fetched and admin-uploaded (`App\Support\SvgGuard`), since they're served from CampBuddy's own origin.
> - **Install / home-screen identity is CampBuddy's, not the event's** *(supersedes the old "install picks up that event's own name/icon")*. `ManifestController` serves the same manifest everywhere — `name` **"CampBuddy | Your WordCamp Companion"**, `short_name` **"CampBuddy"** (strings in `config/campbuddy.php`, not derived from `APP_NAME`) — with CampBuddy's PNG icons (192, 512, maskable 512; the old manifest declared every icon `image/svg+xml`, even PNGs, and used a possibly-wide event logo as the app icon). Installing from an event page still *opens that event* (`start_url` = the event's home; `/manifest.webmanifest` opens the picker); `scope` is `/` so the picker, other events and `/admin` stay inside the installed app. iOS takes its home-screen label from `apple-mobile-web-app-title` ("CampBuddy"), not `<title>`, so the tags in `attendee/partials/head-meta.blade.php` set it explicitly.
> - **Light brand assets.** `public/media/icons/` holds generated PNGs (`icon-192/512`, `icon-maskable-512`, `apple-touch-icon` 180, `favicon-32/48`), `public/favicon.ico` is a real icon (was a 0-byte placeholder), and `logo-wordmark(-sm).png` replace the 560 KB `logo.svg` / 3.3 MB `logo.png` / 1.2 MB `icon.svg` / 0.9 MB `favicon.png` on every page (those originals remain in `public/media/` as the masters — SVG/PNG wrappers around a raster — regenerate the derivatives from them if the brand changes).
