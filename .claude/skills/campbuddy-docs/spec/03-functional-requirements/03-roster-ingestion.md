# 3.3 Attendee roster ingestion

[← Index](00-index.md) · Previous: [3.2 Event branding](02-branding.md) · Next: [3.4 Interest-based matching →](04-matching.md)

| ID | Requirement |
|---|---|
| IN1 | A scheduled job parses one event's public Attendees page HTML and upserts (name, gravatar URL, optional links) keyed by a stable hash of name+links (no upstream ID exists — see risk in [8.4](../08-security-privacy.md#84-ingested-roster-data--explicit-policy)). |
| IN2 | Ingestion runs **once daily per active event**, not more — this is a scrape of someone else's site, not an API with a documented rate limit. |
| IN3 | Ingestion for multiple events is batched with a delay between events (sequential with a cooldown), never parallel-hammering multiple WordCamp sites at once. |
| IN4 | If the page structure changes and parsing fails, the job logs and alerts (via the admin dashboard's fetch-log, same pattern as V1's `fetch_log`) rather than silently ingesting garbage. |
| IN5 | An attendee can request removal from CampBuddy's roster ([8.4](../08-security-privacy.md#84-ingested-roster-data--explicit-policy)) — the ingestion job must respect a local suppression list on every re-run. |

> **Current implementation note (IN2 schedule, and a true mirror):** the daily run is pinned to **midnight** (`dailyAt('00:00')`, in the app timezone — `APP_TIMEZONE`, default UTC) for every `active` event, staggered 10 s per event (IN3), and is worked off by the scheduler's own queue drain ([5.2](../05-system-architecture.md#52-ingestion-flow)). After upserting, the job **removes attendees who are no longer on the source page** — otherwise someone who opted out at the source would stay listed in CampBuddy indefinitely. It never removes suppressed rows (IN5's list is what stops a removed attendee from being re-added), and never prunes on an empty scrape (a page hiccup must not wipe the roster; the next run recovers). The fetch-log message reports how many were removed. The admin's *Purge cache* button deliberately does **not** re-scrape the roster (IN2).

> **Current implementation note (roles on the attendee list, Oct 2026):** each roster entry the API sends now carries `roles` (any of `organizer`, `speaker`, `volunteer`, `microsponsor`, in that order) and, for a speaker, `talks` (up to 3 titles). `App\Support\RosterRoles` works them out once a minute per event: organizers and speakers (the site's REST data) match an entry by **Gravatar hash** — the same picture hash means the same e-mail — and otherwise by an **exact name** (case and spaces ignored) only when that name is on the list once; volunteers (`wcb_volunteer`, fetched with the 15-minute schedule job, names only; a site without them answers 404 and that is not logged as a problem) match by name. **Microsponsors** come from the Attendees page itself: `AttendeeRosterScraper` marks a `.tix-attendee-list` whose block (the list or up to three wrappers) has a class/id like "microsponsor", or a heading saying so while holding no other attendee list (`attendee_roster.is_microsponsor`, migration `2026_10_09_090000`). Rajasthan 2026: 16 organizer, 30 speaker, 19 volunteer, 17 microsponsor entries out of 369. Sponsor *companies* are not people and get no badge. Explore → People shows a badge per role, tints those rows, and adds filter chips above the list (All / Organizers / Speakers / Volunteers / Microsponsors with counts; none when nobody has a role) — `roster-roles.js`, GA `roster_filter` (`filter_value`).

> **Person sheet + card (9 Oct 2026):** tapping a name (a button) or anywhere on a roster row except its links and *+ Meet* opens a bottom sheet (`person-card.js`, `tpl-person-sheet`, `.steal-sheet` styles): photo, name, role badges, a speaker's talks, links, *+ Meet* (the same record as the row's). For anyone with a role it also shows a **card made from public WordCamp info** — the Camp Card's Ticket face (`partials/camp-card-face.blade.php`, `source` on) with the name, the roles as the role line, a speaker's first talk in the "Ask me about" bubble, a QR to their LinkedIn → website → X link (none → no QR), and a small "Made from public WordCamp info" line on the card itself — with **Download card** / **Share** (900 DPI PNG, `camp-card-paint.js`, the Camp Card page's "Preparing… → Ready, tap to …" flow). Nothing is stored or sent. GA `person_card` (`result`: open / download / share), never the name.

> **Roles by hand (10 Oct 2026, owner confirmed twice):** besides the automatic ones, an admin (Admin → Roster → *Roles*) or the event's managers (Manager → *Attendees*, new tab, search + role filter) can tick any of **Organizer, Speaker, Volunteer, Microsponsor, Sponsor, Media Partner, Table Lead** for a person ("auto" shows what was found by itself). `App\Support\RosterMarks` stores only the difference from the automatic answer in `roster_marks` (`add` / `remove`), keyed by the person's Gravatar hash (`g:…`) or else normalised name (`n:…`) so it survives the nightly re-import replacing list rows; agreeing with the automatic answer stores nothing. `RosterRoles::withAutomatic()` builds both answers in one pass; `forEvent()` (cached 60 s) is dropped on a change, as are the roster API pages, so the badge shows on the next request. Manager changes go to the activity log (section `attendees`). New badge colours for Sponsor, Media Partner, Table Lead.
