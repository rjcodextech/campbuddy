# 10. API specification

[← Back to index](../SKILL.md) · Previous: [9. Admin panel](09-admin-panel.md) · Next: [11. Installation & setup →](11-installation-setup.md)

Same envelope conventions as V1 (`/api/v1/*`, public, GET-only except where noted, JSON, cached/rate-limited at the edge). New/changed endpoints:

| Endpoint | Returns |
|---|---|
| `GET /api/v1/events` | Events with `status=active` **and** `is_visible=true` ([3.2](03-functional-requirements/02-branding.md) BR6) |
| `GET /api/v1/events/{slug}` | Single event detail |
| `GET /api/v1/events/{slug}/roster` | Ingested attendee roster (name, gravatar, links) — paginated |
| `GET /api/v1/events/{slug}/discovery` | All active `discovery_profiles` for the event, `discovery_id` + chosen fields only, **never `owner_token_hash`** ([7](07-data-model.md), [8.6](08-security-privacy.md#86-discovery-api-ownership--a-real-gap-caught-and-fixed-here)) |
| `POST /api/v1/events/{slug}/discovery` | Create a new discovery profile — the "Join attendee discovery" action ([3.4](03-functional-requirements/04-matching.md) M2). Response includes the `discovery_id` **and** the one-time-shown owner token. |
| `PATCH /api/v1/events/{slug}/discovery/{discovery_id}` | Update this profile's exposed fields — requires the owner token as a bearer credential. |
| `DELETE /api/v1/events/{slug}/discovery/{discovery_id}` | "Leave attendee discovery" ([3.4](03-functional-requirements/04-matching.md) M6) — same owner-token requirement. |
| `GET /api/v1/events/{slug}/quests` | Quest items for the event — default + event-specific merged ([3.6](03-functional-requirements/06-quest.md)) |
| `GET /api/v1/events/{slug}/offers` | Active offers for that event |
| `POST /api/v1/events/{slug}/offers/{offer}/leads` *(added post-launch)* | Submit a Name/Email/Mobile lead before opening a deal with `capture_leads` enabled — one-shot public write, no owner-token lifecycle. 422 if the deal doesn't have lead capture on. See [3.7](03-functional-requirements/07-deals.md). |
| `POST /api/v1/push/subscribe` | Register a Web Push subscription for a bookmarked session |
| `POST /api/v1/events/{slug}/bookmarks` / `DELETE ...` | Bookmark a session server-side (only needed for reminder scheduling) |
| `GET /api/v1/cache-version` *(added)* | `{"version": "<ms timestamp>"}` — bumped by the admin's *Purge cache & refresh data* ([9](09-admin-panel.md)); `Cache-Control: no-store`. An open app polls it when returning to the foreground and reloads if it changed. `"0"` until the first purge. |
| `GET /api/v1/health` | Health check |

Existing V1 endpoints (`event`, `media`, `sponsors`, `agenda`) become event-scoped: `/api/v1/events/{slug}/media`, etc.

> **Current implementation note:** the mutating routes (discovery POST/PATCH/DELETE, deal leads, **push subscribe**) share the `api-writes` limiter (10/min/IP); everything under `/api/v1` also counts against `api-general` (60/min/IP) — see [8.1](08-security-privacy.md#81-rate-limiting). `push/subscribe` requires an `https` endpoint that isn't a private/internal address. `GET …/roster` returns only `http(s)` links and avatar URLs. Every response carries the security headers in [8.2a](08-security-privacy.md#82a-hardening-pass-full-review).

> **Current implementation note — shared lists are built once and validated (Sept 2026):** `roster`, `discovery` and `data-version` are the same for every visitor, so `App\Support\ConditionalJson` serves them from a short-lived built copy (roster page 60 s, discovery list 20 s, cleared at once when a profile joins/edits/leaves; `data-version` is already cached 120 s in `DataVersion`, whose fingerprint is built from the event's details, information, fetched lists and the *last-updated time and count* of its deals and quests — the counts so that removing an item changes it too, which "last updated" alone cannot show) with a weak **ETag** and `Cache-Control: public, max-age=0, s-maxage=30|15|20, stale-while-revalidate=2×`. A phone holding the current version gets an empty **304**; browsers always revalidate (`max-age=0`). `s-maxage` only matters once a CDN cache rule covers `/api/v1/events/*` (see [12](12-deployment.md)) — until then the headers are harmless. **Never shared:** `cache-version` stays `no-store` (it is the admin purge signal), and a person's own waves/messages (owner-token calls) get no `public`/`s-maxage`. The client polls `data-version` without the old `?t=` cache-buster (which defeated every cache) and with `cache: 'no-cache'`. Tests: `tests/Feature/ApiCachingTest.php`.

> **Current implementation note — `roster_id` on the discovery card (Sept 2026):** each card returned by `GET …/discovery` (and by the create/update responses) has `roster_id`: the id of the attendee-list entry the owner picked as themselves (the same `id` the public `GET …/roster` returns), or `null` for anonymous and typed-name profiles and for a suppressed entry. It is not new information — the card already shows that entry's name, photo and links — but it lets a phone treat the list entry and the match as one person ([3.4](03-functional-requirements/04-matching.md)).

> **Current implementation note — moving to another device (30 Sep 2026, not deployed):** someone who set up CampBuddy on one device and then picks their own, already-linked name on another can move everything across. `POST …/device-transfers` (new device: roster id + ECDH P-256 public key → `transfer_id` + a secret), `GET …/discovery/{id}/transfer` (old device, owner token: the latest waiting request), `POST …/discovery/{id}/transfer/{tid}/approve|decline` (owner token; approve uploads `sender_key`, `iv`, `payload` sealed with AES-GCM under an HKDF-derived ECDH key — the server can't read it), `GET …/device-transfers/{tid}` (new device's secret: status, and the sealed data once approved), `POST …/device-transfers/{tid}/complete` (new device: rotates the profile's owner token and returns the new one, deletes the payload), `DELETE …/device-transfers/{tid}` (new device gives up), `GET …/device-transfers/{tid}/sender` (old device's own secret: learns it's done, then clears its local data). The old device approves only after typing the 6-digit code the new device shows (a hash of its public key), so a stranger's request can't be approved by a tap and a swapped key wouldn't match. Requests last 10 min (finished ones, without data, 24 h), are pruned every 5 min, capped at 6/hour per name and 10/hour per device, and every response is `no-store`. What moves: `kv` (except `notificationState`, `pushEndpoint:*`, `outbox:*`, `roster:*`), bookmarks (reminders arrive switched off), quest progress, met history, meetings, the remembered wave name. The move is offered both when a name shows as taken in *Pick my name* and when *Join* is refused because the phone's saved list was older than the link. The new device keeps its request (with its non-exportable private key) in IndexedDB, so a reload resumes it; the old device remembers an approved move, so closing its popup still clears it once the new device has the data. The new device saves the data *before* completing, so a failure can't leave both devices empty. The admin's *Release claim* is unchanged. Code: `DeviceTransferController`, `DeviceTransfer`, `device-transfer.js`, `transfer-crypto.js`; tests: `DeviceTransferTest`, `tests/js/transfer-crypto.test.mjs`.

> **Added 9 Oct 2026.** `GET …/roster` entries also carry `roles` (organizer / speaker / volunteer / microsponsor), `talks` (a speaker's, up to 3) and `camp_card` (the shared card's fields, or `null`). `POST …/camp-card-share` `{attendee_roster_id, card: {role?, company?, city?, interests?, askMeAbout?, qr?: {type, url}}, discovery_id?, discovery_token?}` → 201 `{share_id, attendee_roster_id, card, owner_token}` (token shown once); `PUT …/camp-card-share/{shareId}` (same body, `Authorization: Bearer <owner token>`) → 200; `DELETE …/camp-card-share/{shareId}` (bearer) → 204. 403 for a wrong token or unknown id alike; 422 when the name is taken, hidden, gone, or someone else's discovery name. Writes use `throttle:api-writes` and drop the cached roster pages.

> **Live announcements (21 Oct 2026, branch `app`, owner confirmed twice).** An admin or the event's manager sends a short "what is happening now" message (presets in `App\Support\EventBroadcasts::PRESETS`: opening remarks, keynote, session starting, panel discussion, tea break, short break, lunch, high tea, group photo, Contributor Day, closing remarks, or their own words; `{where}` / `{session}` filled in). Who gets it: every device that opened that WordCamp in the website, PWA or app from 3 days before its first day until the send (`event_device_visits`, written by `POST /api/v1/events/{slug}/seen` `{device_id, platform}`, at most every 6 h per device) and allowed notifications — Web Push and FCM through `SendBroadcastPushJob` (TTL 30 min, urgency high, opens the event's Home or the preset's tab). Everyone else sees it as a banner "From the organizers" under the top bar for 30 minutes: `GET /api/v1/events/{slug}/live-notice` (cached 15 s, ETag; `data` null when nothing is current), checked every 4 minutes and on return to the page; closing it hides that one announcement on that device. Home shows "Get live updates from the organizers" (turn notifications on) once, from 3 days before the event to its last day, while notifications are off. Limits: one a minute, 40 a day per event. Panels: web Notifications page (admin `admin.events.broadcasts.store`, manager `manager.events.broadcasts.store`, partial `partials/event-broadcast`), app `GET|POST /api/v1/app/organizer/events/{id}/broadcasts` (reach `{web, app, seen}`, presets, upcoming sessions, history; throttle 10/min; manager activity logged) — the native app's "Announce" tab. Tests: `EventBroadcastsTest`, `tests/js/live-updates.test.mjs`, emulator walk (banner, ask card, close, manager send).
