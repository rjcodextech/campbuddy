# 12. Deployment (shared/cPanel hosting, behind Cloudflare)

[← Back to index](../SKILL.md) · Previous: [11. Installation & setup](11-installation-setup.md) · Next: [13. Pre-launch blockers →](13-prelaunch-blockers.md)

**Docroot workaround:** Laravel expects `public/` to *be* the docroot, but many cPanel accounts can't point a domain's document root at a subfolder. Check first — some hosts allow changing it under cPanel → Domains. If not: upload the whole app **above** the public web root, then copy `public/index.php` and `public/.htaccess` into `public_html` and edit the two `require`/`bootstrap` paths in `index.php` to point up to the real `vendor/autoload.php` and `bootstrap/app.php`. This keeps `.env`, `app/`, `database/`, etc. outside the web-servable directory entirely.

**…and tell Laravel where the web root now is.** In that `public_html/index.php`, right after the app is created (`$app = require_once …/bootstrap/app.php;`), add:

```php
$app->usePublicPath(__DIR__);
```

Without it Laravel still thinks `public/` (inside the app folder) is the public path, so the `storage` link ends up *there* — not in `public_html` — and every uploaded or auto-fetched event logo 404s. (This was the production logo bug: the link existed in the local `public/` folder but never on the live site.) With the line in place, the web side — including the Purge-cache button's best-effort attempt — creates `public_html/storage`.

`index.php` is only used by web requests, so **`php artisan storage:link` run from SSH still targets the app's own `public/`**. From a shell, create the link yourself, pointing at the app's `storage/app/public` (adjust the path to where the app sits):

```
ln -s ../campbuddy/storage/app/public public_html/storage
```

> **Current implementation note — logos work even with no link.** `/storage/{path}` is also a Laravel route (`PublicStorageController`): when the web server can't find the file itself (no symlink, or `symlink()` disabled by the host) the request falls through to the app, which serves the image from `storage/app/public` — images only (png/jpg/gif/webp/avif/ico/svg), path-traversal safe, `nosniff`, SVGs with a script-blocking CSP. So a missing link costs a little speed, never the logos. Event image URLs are root-relative (`/storage/branding/1/logo.png?v=<mtime>`), independent of `APP_URL`.

1. Provision Cloudflare (or equivalent) in front of the domain — **do this before go-live, not after** ([5.4](05-system-architecture.md#54-cdn--now-mandatory-not-optional)).
2. Upload the app per the docroot approach decided above (including `usePublicPath`).
3. `composer install --no-dev --optimize-autoloader`, `npm ci && npm run build`, then the storage link (see above — `php artisan storage:link` on a standard docroot, the `ln -s` for the `public_html` workaround; optional, the app serves logos without it).
4. Configure `.env`: DB credentials, fresh `APP_KEY`, VAPID keypair for push, `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL=https://yourdomain` (an `https://` URL also forces every generated link to https), `SESSION_SECURE_COOKIE=true`, `QUEUE_CONNECTION=database`. Optional: `APP_TIMEZONE=…` (the scheduler's "midnight" — the nightly attendee-roster refresh — is midnight in this zone; default UTC) and `CLOUDFLARE_ZONE_ID` + `CLOUDFLARE_API_TOKEN` (lets the admin's Purge-cache button purge Cloudflare too; token scope: *Zone → Cache Purge → Purge* on this one zone, nothing else).
5. Run **`php artisan campbuddy:doctor`** — the one command for every deploy (and any time something looks wrong). It clears every cache and optimisation, empties the logs, installs PHP dependencies if `composer.lock` changed, builds the front end where Node is available (otherwise upload `public/build` built on your computer), runs all pending migrations, re-caches config/routes/views in production, fetches every live event's data (schedule, speakers, sponsors, event info, missing branding, attendee list), and finishes with a health report: cron not running, failed jobs, `APP_DEBUG` left on, events with no data — each with its fix. Options: `--no-build`, `--keep-logs`, `--skip-fetch`. First install only: also seed the admin user (`php artisan db:seed --class=AdminUserSeeder`).
6. cPanel Cron needs **exactly one entry**, running every minute — Laravel's scheduler dispatches each job on its own configured cadence internally, **and drains the queue itself** (its last task, `work-queue`), so no separate queue worker is needed:
   ```
   * * * * * php /path/to/artisan schedule:run >> /dev/null 2>&1
   ```
   **If this cron isn't running, nothing is ever fetched** — no branding, no schedule refreshes, no reminders — because every job is only queued until the scheduler works the queue. See [5.2](05-system-architecture.md#52-ingestion-flow) for each job's actual cadence (discovery every 2 days, lifecycle sweep 01:00, roster midnight, event info 02:00, branding backfill 02:30, sessions every 15 minutes).
7. Confirm Cloudflare is actually caching page and API responses (check `cf-cache-status` header) before calling this done. Re-check the CSRF/cacheability caveat from [5.4](05-system-architecture.md#54-cdn--now-mandatory-not-optional) while doing this. `/api/v1/cache-version` sends `no-store` and must not be cached by any Cloudflare rule. The app trusts proxy headers (`trustProxies(at: '*')`), so per-IP rate limits see each visitor's real IP rather than Cloudflare's edge — keep the origin reachable only through Cloudflare if you can.
8. Confirm `.env`, `composer.json`, `*.sql`, and everything outside `public/` returns 404/403 (or isn't reachable at all, if using the docroot workaround); `/api/v1/health` returns OK.
9. Smoke test after go-live: the picker shows each event's logo/favicon (not CampBuddy's icon); the tab title reads *"CampBuddy | Your WordCamp companion"* on `/` and *"{Tab} | {Event} | CampBuddy"* inside an event; `/manifest.webmanifest` returns 200 with `name` *"CampBuddy | Your WordCamp Companion"* and `short_name` *"CampBuddy"*; Dashboard → **Purge cache & refresh data** completes and reports "fresh data fetched for N events".

**Stale data or a stale logo after a deploy or an upstream change?** Dashboard → *Cache & fresh data* → **Purge cache & refresh data** ([9](09-admin-panel.md)) — it's the supported equivalent of `optimize:clear` + re-ingest + a Cloudflare purge + telling every installed PWA to reload.


> **Current implementation note (stability):** an event's fetched lists are stored permanently in the `event_feeds` table, with the cache only as the fast path (`App\Support\EventData`) — a cache purge or a stopped cron no longer blanks a live event. Event pages also refresh data themselves, after sending their response, when it's missing or over an hour old (at most every 5 minutes per event), and Explore refreshes an attendee list not fetched for a day — so the site keeps working even while the cron is broken. The admin dashboard lists what's wrong (scheduler not running — tracked by a once-a-minute heartbeat — pending migrations, stuck or failed jobs, live events with no data) with the command that fixes each; `/api/v1/health` reports the same as yes/no checks. **Production `.env` must have `APP_DEBUG=false`** — with it on, error pages show visitors the code, database name and server.

> **Current implementation note — caching headers and the one Cloudflare setting they need (Sept 2026):** `public/.htaccess` now sends `Cache-Control: no-cache` for `/sw.js` (it had none, so Cloudflare cached it by extension — a new service worker could take hours to reach phones; after deploying this, **purge `/sw.js` once** at Cloudflare). Every page and API response otherwise carries Laravel's default `no-cache, private`, which Cloudflare **never caches** (and it never caches HTML/JSON by default anyway; `cf-cache-status: DYNAMIC` on the live site). The shared API lists now send CDN-friendly headers ([10](10-api-specification.md)); to make them effective, add **one Cache Rule** at Cloudflare: *URI path starts with `/api/v1/events/` and ends with `/roster`, `/discovery` or `/data-version`* → **Eligible for cache**, Edge TTL **Use cache-control header if present, bypass cache if not**. (Cloudflare Development Mode switches caching off for 3 hours at a time — fine while iterating.) Do not cache `/api/v1/cache-version`, waves, messages or anything under `/admin`.

> **Current implementation note — the service worker switch (Sept 2026):** `public/sw-flags.json` ships as `{"swrPages": false}`. To turn stale-while-revalidate for page opens on (instant opens from the phone's saved pages, far fewer requests to the host), edit that file on the server to `true` — no build or deploy; running workers pick it up within ~10 minutes. To turn it off again set it to `false` or delete the file. Roll it out gradually by watching request volume/errors before and after (`tools/loadtest.mjs`, the host's graphs). It is `no-store` (`.htaccess`) so Cloudflare never holds an old copy.

> **Current implementation note — LiteSpeed (Sept 2026):** the live origin is LiteSpeed (`x-turbo-charged-by: LiteSpeed` on every response). It honours `<Files>` / `<FilesMatch>` and `Header set` in `.htaccess` but silently ignores `<If>` blocks, so the header rules that matter are written that way: `/sw.js` → `no-cache`, `/sw-flags.json` → `no-store`, `/build/manifest.json` → `no-cache` (Cloudflare was serving it as a HIT with no header), hashed build files (`name-<hash>.js|css`) → `public, max-age=31536000, immutable`. Verify after a deploy with `curl -sI https://<site>/sw.js | grep -i cache-control` (expect `no-cache`) and `curl -sI https://<site>/build/assets/<any hashed file>.js` (expect `immutable`). The full launch checklist (commands, Cloudflare settings, tests, rollback) is [`DEPLOYMENT.md`](../../../../DEPLOYMENT.md) in the repo root.

> **Current implementation note — production `.env` review (Sept 2026):** the live `.env` was reviewed against the code; the Sept 2026 work needs no new keys. Worth setting beyond the checklist above: `LOG_LEVEL=warning` (+ `LOG_STACK=daily`; a crowd makes a `debug` log huge — every failed push writes a warning), `GA_MEASUREMENT_ID` (without it the attendee app sends no analytics at all; `GA_PROPERTY_ID` / `GA_CREDENTIALS_PATH` only serve `campbuddy:ga-setup`, and the service-account key can be removed once it has run), and `CLOUDFLARE_ZONE_ID` + `CLOUDFLARE_API_TOKEN` (now that Cloudflare caches the API lists, the admin purge button should clear the edge too). Never change on a live database: `APP_KEY`, the VAPID keypair (all push subscriptions die), `APP_TIMEZONE` (shifts how stored timestamps read), or move `CACHE_STORE` / `SESSION_DRIVER` off `database` mid-event. In production the config is cached (`campbuddy:doctor` runs `optimize`), so after editing `.env` run `php artisan optimize:clear && php artisan optimize`. Per-key table: `DEPLOYMENT.md` → *Server ka `.env`*.

> **Current implementation note — `npm run build` removes `public/hot` (Sept 2026):** the `build` script is now `vite build && node tools/remove-hot.mjs`. `public/hot` is what `npm run dev` writes ("load assets from the dev server on this computer"); left behind and uploaded, it makes every visitor's browser ask a dev server that only exists on the developer's machine, and the site loses its styling (this happened on 26 Sep 2026). The Laravel Vite plugin only removes it when the dev server stops cleanly, so a crashed or closed terminal left it in place. Now a build always ends without it, and `npm run dev` creates it again on start. If `npm run dev` is running while a build is done, the running session loses hot reload until it is restarted; the site itself keeps working from the built files. Also still worth checking after every upload: `curl -sI https://<site>/hot` must be 404.
